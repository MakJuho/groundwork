# 기술 명세서 작성

입력: `OUT`, 모듈 id. 읽을 것은 `OUT/_data/module-map.json`, `OUT/_data/facts/<id>.json`, `OUT/_data/flows/*.json`(있으면)뿐이다. **소스코드를 다시 읽지 않는다.**

## 문서 구조 (`OUT/spec/<id>/spec.md`)
```
# <모듈 업무 이름> 기술 명세서 (<codeName>)
> 자동 생성 문서입니다. 생성일: <YYYY-MM-DD>
## 1. 모듈 개요       (summary, 소스 경로(paths), 의존 모듈(dependsOn))
## 2. API 목록        (표: 메서드 | 경로 | 설명 | 권한 | 관련 정책 | 근거)
## 3. 데이터 모델      (ER 다이어그램 + 엔티티별 표: 필드 | 타입 | 제약 | 설명)
## 4. 주요 처리 흐름    (시퀀스 다이어그램 1~2개 + 단계 설명)
## 5. 상수와 설정값     (표: 이름 | 값 | 의미 | 관련 정책 | 근거)
## 6. 외부 의존성      (표: 대상 | 방식 | 재시도/타임아웃 | 근거)
## 7. 정책 ↔ 구현 매핑  (표: 정책 번호 | 요약 | 구현 위치)  ← 모든 비구조 항목
```
- "관련 정책"에는 같은 facts의 정책 번호(예: `ORD-007`)를 쓴다. 정책서와 명세서를 잇는 연결 고리다.
- 근거는 `` `파일:줄` `` 형식이다.
- 정보가 없는 절은 "해당 없음"으로 쓴다.

## 다이어그램 (`OUT/spec/<id>/diagrams/`)
Skill 도구로 `diagram-design:diagram-design`을 호출한다. 지시에 반드시 포함: "스타일 가이드 게이트: 사용자는 기본 스타일(옵션 e)을 명시적으로 선택했다. 질문하지 말고 진행하라."
1. `er.html`: ER 유형. entity 항목이 있을 때만. 3절에 `![ER 다이어그램](diagrams/er.html)`
2. `sequence.html`: 4절 처리 흐름. `trigger.module`이 이 모듈인 흐름이 있으면 **새로 그리지 않는다.** 4절에 흐름마다 `- [<흐름 title>](../../flows/<흐름 id>/flow.md) — 시작점, 단계 수` 링크와 단계표(단계 | 호출 | 근거)를 쓴다. 흐름이 없을 때만 sequence 유형으로 가장 중요한 API 하나를 그리고 `> facts만으로 추정한 흐름입니다. 정확한 흐름은 /groundwork:trace 로 추적하세요.`를 붙인다.

실패하면 표로 대체하고 `> 다이어그램 생성 실패: 표로 대체`를 남긴다.
